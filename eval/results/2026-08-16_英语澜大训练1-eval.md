| Run 3 | 77.3% / 73.9% / 75.6% | 100% | ⑤ 文本匹配恢复 bbox 后，多题共享同一 bbox → 贪心质心分配饿死后题（FN 6 个全因此） |

### 修复清单

1. **scanner-v3.mjs** `imgToBase64()`: data URL 直通（`/preprocess` 返回的红笔图是 data URL，此前被当文件路径打开 — **该 bug 在生产同样存在，VL 红笔分类一直是静默失败的**）
2. **scanner-v3.mjs** merged 路径: 按 LLM pageIndex 把题目分发回各自页（此前全塞第 1 页）
3. **preprocess-server.py** `/textin/ocr-merged`: 返回带 pageIndex 的 `handwritten_regions`（恢复 v4.5 TextIn 交叉验证）
4. **llm_parser.py** `_recover_missing_bboxes()`: LLM 漏回显 itemIndices 时，用题干/选项文本归一化匹配 OCR item 重建 bbox
5. **llm_parser.py** `_split_shared_bboxes()`: 共享 bbox 垂直均分 + 相邻包含收缩（解决连续小题贪心饿死）
6. **scanner-v3.mjs** Kimi fallback 端点: `api.moonshot.cn` → `dashscope.aliyuncs.com/compatible-mode`（KIMI_API_KEY 实为 DashScope key）

## 残留误差分析

**FP（5 个，全部是"红笔在旁边但题没错"）**: Q6/Q24/Q26/Q65/Q66。该教师批改风格是**每题旁都写红笔字母**（答案键式），纯几何/能量无法区分"写字母=错"还是"写字母=对"。这是当前天花板——需要 VL 分类恢复后读标记类型（✓=对）或读学生原答案与红笔字母对比。5 个 FP 中 Q65/Q66 旁 VL 可见红字母（A/BC/C/B），Q6/Q24/Q26 需人工看图。

**FN（2 个）**: Q12/Q22。运行间波动（Run 3 漏的是 Q11/Q13/Q23/Q25/Q27/Q28，Run 4 换成了 Q12/Q22）——LLM 逐次输出的 questionText 略有差异 → 文本匹配恢复的 bbox 逐次不同。收敛手段：强化 prompt 让 itemIndices 回显率提高（治本），或多次运行投票（治标）。

**题型 13.8% 的真相**: 分类学口径冲突，不是识别错误。GT 用教学口径（阅读理解/完形填空），scanner 用形式口径（choice/cloze/grammar_fill）。同一份卷子：Q1-15 教学上是"阅读理解"，形式上是"语篇填空"（scan=cloze）；Q25-30 教学上是"完形填空"，形式上是"无选项填词"（scan=grammar_fill）。**需要产品决策**：错题本按哪个口径展示？建议 scanner 输出双字段（sectionName 教学口径 + questionType 形式口径）。

1. **VL API key 全部失效（本地）**: Zhipu 401（令牌过期）、DashScope 401（invalid key）。需更新 `.env`。VL 分类恢复后预期还能消化部分 FP（✓ 标记识别）。
2. **LLM 运行间方差**: 4 次运行 questionText/bbox 有波动。建议 prompt 中把 itemIndices 列为必填+自检项。

4. **服务器部署**: 本次 6 项修复需 deploy 后生产才能受益（尤其 imgToBase64 — 生产 VL 分类同样静默失败中）。
