# gaozhong.online — 错题识别流水线深度分析文档

> 版本: 2.0 (2026-05-13)
> 定位: 对已开发程序、当前执行方案、未来新方案的系统性技术分析
> 目的: 梳理每个环节的处理逻辑、存在问题、解决方案，为最终决策提供依据

---

## 1. 产品定位（不变）

**不做批改。** 学校/学生自己做批改动作。只做「阅读已有批改标记 → 判定对错 → 整理分析」。

核心价值：帮学生减负提效，把已批改的试卷变成结构化的错题本 + 知识点地图。

**最终质量标准**：通过人机协同达到 100% 准确率（复核后），自动化部分目标 ≥80% 精确率、≥85% 召回率。

## 2. 迭代历史总览

```
v1-v5 (4/27-5/2)   作文批改模块，OpenCV+PaddleOCR 初版，红笔分离问题多，退回
v6-v7 (5/2-5/9)    红笔突出图 + VL 单页扫描，过度检出严重（8→32道误判）
v7.1 (5/9-5/11)    红笔突出图+VL单页扫描→DeepSeek，为生产版本
v8 (5/11)          paper-scanner-v8.js：三阶段（区域+裁剪双图判错），写了但未接入生产
v1.0 scanner (5/12) 当前生产版本：阶段1 VL切题→阶段2裁剪批处理VL判错→阶段3 DeepSeek纯文本
```

**关键教训**：
- OpenCV+PaddleOCR 初版因红笔分离质量和手写OCR准确率问题被放弃
- VL 整页扫描的过度检出问题反复出现，根源是印刷答案键混淆
- 三阶段架构（切题→裁剪判错→DeepSeek）方向正确，但 VL 在裁剪小图上仍受印刷答案键干扰

```
    ↓                      ↓
  入库 → 前端展示 → 人工复核
```

## 4. 环节1：图片预处理

### 4.1 处理逻辑

| 方案 | 逻辑 | 状态 |
|:---|:---|:---|
| **方案A: Flask OpenCV预处理** | 色彩校正 + HSV红笔分离 + 红笔突出图生成。调用宿主机 Flask 5001 服务 | v7.1 使用，v1.0 已删除 |
| **方案B: 无预处理** | 原图直接送 VL，不做任何预处理 | v1.0 当前使用 |
| **方案C: PaddleOCR颜色分离** | HSV色相分离→黑/蓝笔通道+红笔通道，分别送OCR和符号检测 | 新方案提案 |

### 4.2 方案A 问题分析

```
问题1: 红笔分离造成断笔/伪影，污染 VL 判断
  - yingyu33 p1: 红笔分离后全部标记变成 ✓，丢失了上下文信息
  - 根源: 颜色分离是像素级操作，无法区分"红笔打叉"和"红色印刷字母"

问题2: 跨服务调用增加延迟
  - Flask 5001 每次调用 3s/页
  - 增加了部署复杂度（两个服务需要协调运维）

问题3: 分离图丢失语义
  - 白底红笔图 → VL 只看颜色，不看笔迹关系
  - 无法区分"红笔划掉学生答案"和"红笔画了无关的线"
```

### 4.3 方案B 问题分析

```
问题1: 原图直接送 VL，token 消耗大
  - 一张 300KB JPEG → base64 约 400KB → VL token 计价
  - 双图（原图+红笔图）调用已被废弃，单图仍有一定成本

问题2: 无红笔像素预检
  - 全白页/笔记页（无红笔）也会走完整 VL 流程
  - 浪费 API 调用和等待时间
```

### 4.4 方案C 优势

```
优势1: 本地处理，零 API 成本
优势2: 分离后可分别处理（黑/蓝→OCR，红→符号检测）
优势3: 颜色分离 + HSV 阈值可以精确控制，比 VL 视觉判断确定性强
```

### 4.5 环节1 决策

**当前 v1.0 方案B 可维持，但应补充红笔像素预检（OpenCV HSV 快速判断有无红笔，跳过全白页）。**
**新方案（PaddleOCR+符号检测）需要方案C的颜色分离能力，但需注意之前的断笔/伪影问题是否已解决。**

### 5.2 方案A 问题分析

```
未修复风险:
  - 不同版面风格的试卷，VL 可能再次误判布局

```

### 5.3 方案C 潜在问题

```
PaddleOCR 版面分析:
  优势: 基于文本框检测，确定性高
  风险: 
  1. 无法理解"题目语义边界"（两个文本框属于同一题还是两题？）
  2. 对选择题的 "A. xxx  B. xxx  C. xxx  D. xxx" 可能识别为多个独立文本框
  3. 需要设计规则将文本框合并为题目区域
```

## 6. 环节3：红笔标记检测

### 6.1 处理逻辑

| 方案 | 逻辑 | 精确率 | 召回率 | 状态 |
|:---|:---|:---|:---|:---|
| **方案A: VL 阶段1同时检测** | VL 全图→输出 redMarks[] (类型+bbox+内容) | ❌ 极低 | ❌ | v3 测试后废弃 |
| **方案B: VL 裁剪图判错(当前)** | VL 裁切小图→红笔检测+判错合一 | ~25% | ~33% | v1.0 生产 |
| **方案C: OpenCV 符号检测** | HSV红笔通道→二值化→轮廓分析→形状分类(勾/叉/线) | 待测 | 待测 | 新方案核心 |
| **方案D: 微型YOLO** | 自训练YOLOv11-nano ONNX → 5类标记检测 | 未验证 | 未验证 | 已否决(数据量) |

### 6.2 方案A 问题分析（核心失败）

```
核心失败模式: VL 全局红笔检测完全不可靠

yingyu33 p1 (v2测试):
  检测到 32 个红笔标记 → 全部分类为 "check"
  实际: 有 check、strikethrough、correct_answer 多种类型
  根源: VL 对"红笔突出图"的颜色敏感，忽略标记语义

yingyu34 (v3测试):
  检测到 54 个红笔标记 → 22 cross + 22 correct_answer
  实际: 这些都是右栏印刷答案键（整齐排列的字母），不是教师批改
  根源: VL 无法区分印刷红字和手写红笔

yingyu34 (v5测试 纯切题):
  阶段1 不检测红笔 → 裁切小图送 VL → VL 在裁切图中仍然分不清印刷vs手写
  根源: 裁切图 550px 宽，包含了右栏印刷答案键 → VL 在本地上下文也分不清
```

### 6.3 方案B 当前效果

```
v1.0 生产测试 (yingyu34, b2cb4693):
  检出 8 道错题，匹配真相 2 道
  精确率 25%，召回率 33%
  
  误判原因: Q21/Q27/Q29/Q30/Q31/Q33 在裁切图中包含了印刷答案键
            VL 将印刷字母误判为教师手写批改
  漏判原因: Q24/Q40/Q41/Q44 的教师手写批改被"忽略印刷"规则错误过滤
```

### 6.4 方案C 设计

```
OpenCV 符号检测流程:
  1. HSV 色相分离 → 提取红色通道二值图
  2. 形态学操作（闭运算去除噪点）
  3. 轮廓检测 → 提取每个红笔区域的几何特征
  4. 形状分类:
     - 两条交叉线 + 夹角 45-135° → cross (✗)
     - 向上弯曲弧线 + 端点比底点高 → check (✓)
     - 长宽比 > 3 + 直线 → underline/strikethrough
     - 不规则形状 + 小面积 → 候选文字区域

  优势: 确定性计算，不受印刷字体干扰（印刷字母有固定形状）
  风险: 
    1. 潦草符号识别率下降
    2. 符号重叠（✗重叠在文字上）→ 轮廓无法分离
    3. 需要针对不同红笔颜色调 HSV 阈值
```

### 6.5 环节3 决策

**当前 v1.0 方案B 是最大瓶颈（25% 精确率），根源是 VL 无法区分印刷和手写红笔。**
**新方案C（OpenCV符号检测）是核心突破点——确定性计算天然免疫印刷干扰。**
**建议混合：OpenCV 做 90% 的符号检测，不确定的裁切送 VL 确认（低成本二次确认）。**

## 7. 环节4：对错判定

### 7.1 处理逻辑

| 方案 | 逻辑 | 状态 |
|:---|:---|:---|
| **方案A: VL 直接判错** | VL 看图→输出 isError + studentAnswer + correctAnswer | v7.1 使用，v1.0 废弃 |
| **方案B: VL 裁切图判错(当前)** | VL 看裁切小图→输出 isError + answer + teacherIntent | v1.0 生产 |
| **方案C: 规则引擎** | 代码根据红笔标记类型+OCR文字执行决策树 | `error-identification-logic.md` 已有 |
| **方案D: 混合** | OpenCV/OCR提供证据→规则引擎判定→VL二次确认低置信 | 新方案 |

### 7.2 现有规则引擎（可直接复用）

```
判定规则 (source: error-identification-logic.md):

1. 红笔 ✗ 打叉 → ❌ 错题
2. 红笔划掉学生原答案 + 写了新答案 → ❌ 错题
3. 红笔写了正确答案字母(手写)且≠学生选择 → ❌ 错题
4. 红笔扣分标记(-2/-0.5) → ❌ 错题
5. 红笔 ✓ 打勾 → ✅ 对
6. 红笔只圈出/下划线/注释(无✗无更正) → ✅ 对
7. 此题无任何红笔标记 → ✅ 对（需标记为"未批改"，供复核）

置信度输出:
  cross/strikethrough + OCR确认答案不同 → 高置信 ❌
  check + 无其他标记 → 高置信 ✅
  只有 correct_answer 无 cross → 中置信（需对比学生答案）
  无任何红笔 → 低置信（可能是漏批，需复核）
  OCR 置信度低 → 低置信（文字可能读错）
```

### 7.3 环节4 决策

**规则引擎是正确方案，当前已有 `error-identification-logic.md` 和 `assessConfidence()`。**
**新方案只需改变输入源：从 VL JSON → PaddleOCR文本 + OpenCV符号检测结果。**
**规则引擎核心逻辑不变，可直接复用。**

## 10. 关键风险与新方案的应对

### 10.1 手写OCR准确率不足 → 三级策略

```
第1级: PaddleOCR 手写英文模型微调（用已有试卷数据，免费）
第2级: 对低置信度OCR结果，裁切小图送 VL 二次识别（仅读文字，不判对错）
第3级: VL 也无法确定 → 标记低置信，进人工复核
```

### 10.2 潦草勾叉符号 → OpenCV + VL 混合

```
OpenCV 轮廓分析 → 清晰形状(90%) → 直接判定
                → 模糊形状(10%) → 裁切送 VL 确认（¥0.004/张）
```

### 10.3 新方案可能不如 VL 的特定场景

```
场景: 字迹极度潦草 + 符号重叠严重 + 光照不均
风险: PaddleOCR + OpenCV 同时失效，不如 VL 端到端
应对: 保留 VL 作为 fallback 通道（当前 v1.0 代码保留，可随时切回）
```

## 12. 实施建议

### 不着急动手，先验证两个核心假设：

```
假设1: PaddleOCR 手写英文在我们试卷上的准确率 ≥ 70%
  验证: 取 5 张已有试卷，用 PaddleOCR 跑手写识别，人工对比

  验证: 取 5 张已有试卷裁切出的红笔符号区域，跑 OpenCV 分类

两个假设都验证通过 → 可以实施新方案
任一假设不通过 → 需要评估替代策略（如继续优化 v1.0 VL）

```
